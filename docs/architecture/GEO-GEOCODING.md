# GEO-04R — Geocoding Provider Benchmark Contract

## Status

Benchmark tooling implemented. **No production geocoder is selected yet.**

The purpose of GEO-04R is to prevent DUTRA OS from locking persistent CRM coordinates to a provider merely because its demo looks good.

## Non-negotiable legal filter

A provider is eligible for canonical persistent geocoding only when its current terms allow DUTRA OS to store and reuse the result for its own business purpose.

### RECOMMENDED benchmark candidates

#### Geoapify

Current documented properties checked on 2026-10-05:

- geocoding results may be stored;
- OpenStreetMap/data-source attribution must be preserved/displayed as required;
- Free plan: 3,000 credits/day;
- Free plan can be used commercially within its limits;
- Geocoding: 1 request = 1 credit;
- Free-plan rate limit: up to 5 requests/second.

References:

- https://www.geoapify.com/geocoding-api/
- https://www.geoapify.com/pricing/
- https://apidocs.geoapify.com/docs/geocoding/forward-geocoding/

#### Mapbox Permanent Geocoding

Current documented properties checked on 2026-10-05:

- temporary geocoding results cannot be cached/stored;
- permanent results can be stored indefinitely;
- use `permanent=true`;
- permanent storage requires an eligible/billable account;
- current public pricing page lists Permanent Geocoding at USD 5.00 / 1,000 requests for the first 500,000 requests.

References:

- https://docs.mapbox.com/api/search/geocoding/
- https://docs.mapbox.com/help/dive-deeper/understand-temporary-vs-permanent-geocoding/
- https://www.mapbox.com/pricing

The DUTRA benchmark refuses Mapbox calls unless `MAPBOX_PERMANENT_ALLOWED=1` is explicitly set. This prevents a developer from accidentally running non-storable/ambiguous benchmark traffic.

### AVOID as canonical persistent provider

#### Google Geocoding

Current Google policy generally restricts prefetching/caching/storage of Geocoding API content; place IDs are an explicit storage exception.

That makes it a poor canonical coordinate source for this architecture even though Google Maps can remain useful as renderer/navigation UX.

Reference:

- https://developers.google.com/maps/documentation/geocoding/policies

#### Public OpenStreetMap Nominatim

The public server is not a production bulk geocoder for DUTRA OS:

- absolute maximum 1 request/second;
- bulk/periodic jobs are discouraged/restricted;
- commercial applications should consider third-party/self-hosted alternatives.

Reference:

- https://operations.osmfoundation.org/policies/nominatim/

## Benchmark dataset

A provider decision requires **at least 80 manually verified coordinate references** and at least 5 references in every required bucket.

Target set is 100–150 cases.

Required buckets:

- CAPITAL
- INTERIOR
- INDUSTRIAL
- HIGHWAY
- RURAL
- NO_NUMBER
- COMPLEMENT

The verified truth must not be generated by the same provider being evaluated.

A case has:

- normalized address input;
- one primary stress bucket;
- manually verified latitude/longitude;
- allowed tolerance in meters;
- source/provenance of the truth;
- optional notes.

Private/customer benchmark fixtures must not be committed.

## Scoring

Provider-native confidence is never accepted as truth by itself.

DUTRA derives quality from three dimensions:

1. deterministic component agreement;
2. provider confidence/match metadata;
3. returned spatial precision.

Current weights:

- address-component agreement: 55%;
- provider signal: 30%;
- precision signal: 15%.

Hard caps apply to country/state/city mismatches.

### Precision mapping

Canonical precision:

- ROOFTOP
- ADDRESS
- STREET
- POSTAL_CODE
- NEIGHBORHOOD
- CITY
- REGION
- UNKNOWN

Geoapify building-level matches map to ADDRESS rather than claiming ROOFTOP without stronger evidence.

Mapbox may map an address to ROOFTOP only when its `coordinates.accuracy` explicitly reports rooftop.

## Auto-accept contract

AUTO_ACCEPTED requires all of:

- no hard geographic mismatch;
- precision ROOFTOP or ADDRESS;
- component score >= 0.85;
- internal confidence >= 0.86.

Otherwise:

- confidence >= 0.50 → NEEDS_REVIEW;
- lower/no result → UNVERIFIED.

Low precision must remain visually distinguishable and should not be used as a trusted visit/navigation point.

## Benchmark winner rule

The runner does not choose a winner unless ground truth is sufficient.

Technical score combines:

- within-tolerance rate: 40%;
- address-level precision rate: 20%;
- component agreement: 20%;
- auto-accepted rate: 10%;
- success rate: 10%.

If the top two providers differ by less than 0.05 in final score, the decision is `MANUAL_REVIEW_TIE`.

Cost/terms are then a business tie-breaker, never a substitute for data quality.

## Execution economics

The runner is sequential by default and uses a delay between requests.

Recommended first real run:

- 100 verified addresses;
- Geoapify: 100 requests, normally within current free quota;
- Mapbox Permanent: 100 requests, about USD 0.50 at the current public USD 5 / 1,000 tier, subject to account eligibility/current pricing.

No benchmark provider is called by CI.

## Implementation

Shared normalization/scoring:

`supabase/functions/_shared/geocoding.mjs`

Runner:

`scripts/run_geocoder_benchmark.mjs`

Fixture template:

`scripts/geocoding/benchmark-br.template.json`

Run fixture validation without spending API calls:

```bash
node scripts/run_geocoder_benchmark.mjs --dry-run
```

Real provider calls require server/local environment keys and an intentionally prepared verified fixture.

## Decision state

**Geoapify is the current MVP favorite on storage rights and entry cost, but it is not promoted to production until Brazilian benchmark quality is proven.**

Mapbox Permanent remains the higher-cost comparison/fallback candidate.
